# 설계 초안 — AI 규격 왕복 패치 (부분 수정 가져오기)

> 2026-07-29, 회사 노트북 세션 설계 논의 정리. **미구현.**
> 배경 피드백: "가이드 정보량 과다, 상태창까진 쉬운데 이벤트부터 머리 아픔" +
> "AI 규격 내보내기로 받아온 걸 가져오면 통으로 바뀌어 일부 수정이 안 됨".

## 문제 진단

- 현행 탭별 가져오기 = `pickTabFragment` + `Object.assign` → **섹션 통 교체** (test-tabai.js:174).
  일부만 고칠 수 없고, 기존 항목이 조용히 날아간다.
- 탭 분리는 "AI 실수 확률"을 낮추려던 장치인데, 이벤트를 만들면 변수가 따라 필요해서
  **교차 의존이 탭 경계를 무시한다.** 유저는 결국 나머지를 손으로 잇게 됨.
- 재진단: AI 실수는 **출력량**에 비례하지 참조 범위에 비례하지 않는다. 통짜 재출력이
  위험한 건 안 고칠 부분까지 다시 쓰게 해서다. → 해법은 범위 축소가 아니라
  **패치 출력 + 검증/diff 게이트.** (탭 분리는 실수를 *줄이는* 장치, 검증+diff는 *잡는* 장치)

## 원칙

1. 단위는 탭이 아니라 **요청** ("산적 습격 이벤트 추가") — AI는 필요한 섹션을 자유로 넘나든다
2. 출력은 통짜가 아니라 **패치** (추가/변경분만)
3. 안전장치는 AI의 협조가 아니라 **병합 검증 + diff 미리보기** — 협조 안 해도 안 부서지게

## 1. 내보내기 뭉치 (클립보드 1회분 = 인라인 스킬)

- 규격 중 **요청 관련 섹션** (기존 탭별 규격서 재활용 — buildTabExportPrompt 기반)
- **다이제스트**: 통짜 스키마 대신 — 변수 id·타입·라벨·cmd 목록, 이벤트 id + when 한 줄,
  액션/판정 id 목록, mentions 낱말 목록. statusUI HTML/CSS는 제외 (베리디아급 2,700줄의 절반)
- **기존 id 명시 + 지시**: "이 id들은 사용 중. 기존 항목 수정 의도가 아니면 새 id를 지어라"
- allow 편입 기준 요약 (schema.md "넣는다/뺀다" 표) — AI가 판정값·플래그를 allow에 넣는 사고 예방
- 이벤트 시작/끝 짝 원칙 등 안티패턴 경고 (재발동 루프)
- 출력 형식 지시 (아래 패치 형식) + 코드펜스 벗기기는 기존 처리 재사용

## 2. 패치 형식

```js
{
  patchVersion: 1,               // 형식 진화 대비
  add:    { vars: [...], rules: { events: [...] }, actions: [...] },
  update: { vars: [...] },       // 기존 id만
  remove: { events: ['old_id'] } // 삭제는 명시로만
}
```

- **add/update 분리 = INSERT vs UPDATE.** upsert(같은 id 조용히 교체) 금지
- update는 **항목 단위 통 교체** — 항목 내부 부분 패치는 안 한다 (단순성)
- 병합 대상 = id 있는 목록 전부: vars / derived / rules.events / randomEvents.table /
  directives / actions / checks (+ updater.allow는 변수 id 키)
- **예외**: `rules.onTurn[]`은 id가 없음 → v1 병합 제외 (통 교체 유지). statusUI → §6

## 3. 병합 검증 규칙

| 상황 | 처리 |
|---|---|
| add인데 id 이미 존재 | **충돌 정지** → §4 3지선다. 조용한 교체 절대 금지 |
| update인데 id 없음 | 오류 — AI가 없는 걸 고치겠다고 함 (헛짚음 감지) |
| update가 타입 변경 (int→text 등) | **강한 경고** — 기존 채팅 세이브 값과 충돌 |
| remove 대상 없음 | 경고 (무해하지만 헛짚음 신호) |
| 병합 후 | 기존 `validateSchema` 전체 통과 필수 (cmd 중복·mentions 겹침·미지 id 전부 기존 검증이 잡음) |

**원자성**: 패치는 전체 적용 아니면 전무. 부분 적용은 참조 무결성이 깨진다
(이벤트는 들어갔는데 그 이벤트가 쓰는 변수가 거부된 상태).

## 4. add 충돌 해소 (핵심 시나리오)

> 공홈 새 챗에서 "딴거 만들어줘" → AI는 이전 패치를 모름 → 그럴듯한 같은 id 재생성
> → 기존 항목과 우연 충돌. **가장 흔할 사고 패턴.**

diff 화면에서 기존 vs 새 항목 나란히 (label + 식 요약) → 유저 선택:
- **교체** — 의도된 수정이 맞을 때
- **새 id로 추가** — `bandit_raid_2` 자동 개명. **패치 내부에서 그 id를 참조하는 다른
  항목도 일괄 개명** (식에서 id 뽑는 AST 파서 재활용 — 기존 재료로 됨)
- **건너뛰기**

판별 힌트: id 같은데 label이 전혀 다르면 "다른 항목 같습니다" 배지.

## 5. 적용 UX

- **diff 미리보기**: "변수 2 추가 / 이벤트 1 교체 / 삭제 1" + id 나열 → 확인 후 병합
- **remove는 기본 미선택** — AI가 유저 요청 없이 삭제를 끼워 넣는 것 방어
- **적용 전 백업 1슬롯 + 되돌리기 버튼** — 교체/삭제 후회 대비. 백업은 스키마만
  (상태 스냅샷은 별개)
- 적용 직후 **진단 자동 실행** → 경고 즉시 표시

## 6. 열린 문제 / 범위 결정

- **statusUI 사각**: add로 변수만 추가되면 상태창에 안 보인다. 후보 ①
  `statusUI.groups[].items`도 id-키 병합 지원 (그룹 지정 + 항목 추가, 커스텀 HTML 템플릿은
  제외) ② v1은 "추가된 변수 N개는 상태창 탭에서 배치하세요" 안내만. — 구현 난이도 보고 결정
- **라이브 세이브 정합**: 새 변수는 다음 턴 init으로 채워지는지 엔진 확인 필요.
  제거된 변수의 스냅샷 잔존값은 무해한지도. 적용 시점 = "다음 전송부터" 명시
- **연속 패치 stale**: 패치 적용 후 옛 내보내기를 재사용하면 update가 낡은 기준일 수 있음
  → 가이드로 "적용 후 다시 내보내기" 안내 (기술적 방어는 과함)
- 이벤트 평가 순서: 추가분은 배열 뒤에 붙음 — 대부분 무해, 문서에 명시

## 7. 고아 스캔 (검증 탭 — 추가 방식의 부작용 청소)

추가 위주로 쓰다 보면 버려진 변수/이벤트가 쌓인다.

- 검증기가 이미 걷는 참조 그래프(checkExpr + allIds)의 **역방향**: "이 id를 읽거나 쓰는 곳이
  하나라도 있나". 참조면 전부 세야 오탐 없음 — 식(derived/rules/actions/checks/choices) +
  상태창 템플릿 `{변수}` + updater.allow + mentions + cmd + setup.presets + promptState
- **오탐 1순위**: mystery `truth`처럼 스키마에선 안 읽히고 프롬프트로만 나가는 변수
- **정보성 목록 + 항목별 체크 + diff**로만. 자동 삭제 금지
- 진단에 넣으면 **템플릿 전체 오탐 0 확인 후 출시** (v0.28·v0.30·v0.38.2 원칙)

템플릿 9종 고아 스캔 오탐 0 + 가이드 원고 갱신. 기존 탭별 통 교체 경로는 유지
(전면 재작성 용도) — 패치 가져오기는 **별도 입구**로 추가.
