# 설계 초안 — 시간·날짜 1급 지원

> 2026-07-30, 선라이즈 맨션 실전에서 이어진 설계 논의 정리. **구현됨(v0.49~) — 이 문서는 설계 초안이며, 실제 규약은 `.claude/skills/simcore/references/schema.md`의 time 절이 기준.**
> 배경 제보: "1아웃풋당 하루는 설계가 좀 잘못된듯. 보통 그렇게 넘기는 경우가 아예 없다시피 해서 —
> 의도적으로 다음날이나 며칠 뒤 이런식으로 넘기지" + "아예 날짜 다루는걸 만드는게 나을지도.
> YYYY_MM_DD 이 형식은 사람들이 꽤나 선호하는 방식이라서. 24HH:MM:SS도 그렇고".

## 문제 진단

지금은 봇마다 시간을 **손으로 다시 만든다.** 맨션봇(실측) 기준:

```
vars:    day(int) · clock_h(int 0~23) · clock_m(int 0~59)
derived: sim_year · sim_month · sim_dom · sim_season   ← 매번 다시 짠다
onTurn:  day + 1                                       ← 이게 사고의 진원지
```

여기서 실제로 터진 것들:

1. **1턴=1일 전제가 장면 단위 RP를 부순다.** `onTurn`은 출력 1회마다 도니 **메시지 하나 = 하루**가 된다.
   30메시지에 한 달이 지나가고 월세일·생리주기·계절이 그 속도로 휩쓸린다. 실측 사고.
   - 템플릿 실측: `onTurn day+1`을 가진 것은 **survival · romance · vtuber** 셋.
     survival은 장르상 맞지만 **romance는 틀렸다** — 맨션봇이 그걸 상속했다.
   - 반대로 `daily`는 이미 정답 형태다: `day.desc = "[💤 하루를 마친다] 버튼으로만 넘어간다.
     AI는 못 건드린다"` · onTurn 비어 있음 · allow에 없음 · 액션 하나만 `day+1` · `time`은 enum(새벽~밤).
     **정답이 한 템플릿에만 있고 전파되지 않았다.**
2. **자릿수를 채울 수 없다.** `fmtNum`은 천단위 콤마만 넣는다 (render.js). `clock_m = 5`면 "5"로 뜨고
   `07:05`를 만들 방법이 없다 — 맨션봇이 `clock_h` 라벨을 "시각", `clock_m` 라벨을 ":"로 붙여
   두 칸으로 우회한 이유. 게다가 `day`가 1000이면 "1,000일차"가 된다(날짜에 콤마는 방해).
3. **진짜 달력이 아니다.** 30일 × 12달 = 360일. 그래서 **요일이 없다** — 히로미의 "주 1회 파견
   일용직", 주말, 월말 정산 같은 설정을 시스템이 못 받쳐 준다. 생일 "11-08"과의 대조도 어긋난다.
4. **AI에게 날짜 산술을 시키는 유혹.** 날짜를 text로 두면 모델이 월말·연말 롤오버를 계산해야 한다.
   규격서가 못박은 금지사항이 정확히 그것 — "'지금 날짜 + 기간'을 계산시키지 마세요.
   그게 이 플러그인이 없애려는 일입니다."
5. **자정 넘김 배선을 매번 짠다.** 시각이 되돌아가면 하루 지난 것 → 직전 시각 변수 + 이벤트 2개.
   봇마다 다시 발명하고, 발명할 때마다 배선이 어긋난다 (실측: 플래그를 **보조**가 세워야 하는데
   규칙을 **지시문**(=메인 전용)에 써서 매 턴 켜짐 → 여전히 날짜가 튐).

## 원칙

1. **내부는 정수 하나, 표시는 포맷.** 저장·산술·세이브 호환이 전부 자명해진다.
2. **달력 계산은 엔진이 한다** — 윤년·월별 일수·요일. 순수 함수라 테스트가 쉽고 시드와 무관하다.
3. **진행은 양(量)으로 받는다.** AI는 "며칠/몇 분 지났나"만 답한다 — **날짜 산술은 절대 안 시킨다.**
4. **expr에 날짜 타입을 넣지 않는다.** 미니 표현식에 Date를 들이면 복잡도가 폭발한다.
   **파생으로 숫자·문자열을 뽑아 주는 것까지가 적정선.**
5. **옵트인.** `time`이 없으면 아무것도 안 바뀐다. 기존 `day` 관례를 깨지 않는다.

## 스키마 (초안)

```json
"time": {
  "start": "2026-04-01 07:30",
  "advance": "explicit",
  "format": { "date": "YYYY-MM-DD", "clock": "HH:mm" },
  "weekdays": ["월", "화", "수", "목", "금", "토", "일"],
  "expose": ["date", "clock", "weekday", "season", "month", "dom", "hour", "minute", "elapsed"]
}
```

- `start` — 작중 시작 시점. 내부 저장은 여기서 계산한 **epoch(분 단위 정수)** 하나.
- `advance` — `"explicit"`(기본, 명시적 진행만) / `"perTurn"`(구 호환: 턴마다 하루).
- `format` — `YYYY-MM-DD` `YY/MM/DD` `M월 D일` / `HH:mm` `HH:mm:ss` `H시 m분` 등. **자릿수는 포맷이 책임진다.**
- `expose` — 아래 파생을 자동 생성한다. 조건식에서 그대로 쓸 수 있다:
  `hour >= 22` · `weekday == "토"` · `dom == 1` · `season == "겨울"`.
  이름 충돌이 나면 검증이 거부한다 (봇에 이미 `month` 변수가 있으면 알려 준다).

| 노출 | 타입 | 예 |
|---|---|---|
| `date` | text | `2026-04-01` |
| `clock` | text | `07:05` |
| `weekday` | text | `수` |
| `season` `month` `dom` `hour` `minute` | text/int | `봄` `4` `1` `7` `5` |
| `elapsed` | int | 시작으로부터 경과 일수 (구 `day` 자리) |

## 진행 — 두 입구

```json
"add": {
  "vars": [
    { "id": "skip_day", "label": "건너뛸 일수", "type": "int", "init": 0, "min": 0, "max": 30,
      "desc": "며칠 통째로 지났나. 같은 날 안이면 0. 자고 일어나 이튿날 아침이면 1. 2 이상은 '며칠 뒤'류 명시적 도약만." },
    { "id": "skip_min", "label": "흐른 시간(분)", "type": "int", "init": 0, "min": 0, "max": 1440,
      "desc": "이번 장면에서 흐른 시간. 대화 한 토막이면 5~20, 식사·외출이면 60~180." }
  ]
}
```

- **일과 분을 분리한다.** 분 하나로 통일하면 "3일"이 4320이 되어 AI가 곱셈을 해야 한다 — 원칙 3 위반.
- 엔진이 소비: **전송 단계 1.5**(액션이 굳힌 분)와 **응답 단계 5.5**(보조 추정) — onTurn·이벤트 **앞**이라 새 날짜 조건이 그 턴에 발동한다.
  `epoch += skip_day*1440 + skip_min` → 둘 다 0으로 리셋. (초안 때는 "매 턴 끝"이었다 — 2026-10-09 점검에서 정정)
- `maxGain` 캡이 걸린다. **bool 플래그로는 캡을 못 걸었다** — int인 이유 중 하나.
- **버튼 경로도 같은 변수를 쓴다**: `🌙 하루를 마친다` = `skip_day = 1` + `skip_min = 0`.
  daily 템플릿의 방식이 그대로 살아난다.
- ⚠ **이 규칙은 `desc`에 쓴다.** 지시문(directives)은 **메인 모델 전용**이라 보조가 못 읽는다 —
  실측 사고의 원인. `desc`는 보조 프롬프트의 변수 줄 끝에 실린다 (engine.js `buildAuxPrompt`).

## 기존 봇 마이그레이션

- `time`이 없으면 **아무 변화 없음.** 지금 봇 전부 그대로 돈다.
- 편집기에 `[시간 체계 켜기]` — 켤 때 `day`·`clock_*`·`sim_*` 계열을 감지해 **정리 마법사(v0.45)**로
  넘긴다. 참조까지 걷어내는 배선이 이미 있으니 재사용.
- 목록 기한(`@숫자`)은 **절대 시점**이라 그대로 호환된다. 단 단위를 명시해야 한다 —
  `day` 기준이던 것이 `elapsed` 기준인지 epoch 분 기준인지. **v1은 `elapsed`(일) 유지**가 안전하다.

## ⚠ 진단과의 충돌 (가장 중요한 함정)

`advance: "explicit"`이면 **진단 시뮬에서 시간이 안 흐른다.** 진단은 보조 AI를 안 돌리고
액션도 일부만 누르므로 `skip_day`가 영영 0이고, 그러면:

- 월세 청구(`dom == 1`)·급여(`dom == payday`)·계절 이벤트가 **전부 "죽은 이벤트"로 신고**된다
- 날짜 파생만 참조하는 변수가 "안 움직임"으로 신고된다

이미 같은 계열의 오탐을 겪었다 (보조 AI 미실행 → AI 담당 변수가 전부 "안 움직임"). 대책:

- 진단이 `time.advance`를 읽어, `explicit`이면 **시뮬 중 하루 1일 자동 진행을 가정**한다
  (또는 진단 옵션에 "작중 하루/턴" 값을 둔다)
- 그러고도 안 뜨는 날짜 이벤트는 "후반부 이벤트"로 강등 (기존 `onlyLonger` 경로 재사용)
- **전 템플릿 오탐 0 확인 후 출시** (v0.28·v0.30·v0.38.2·v0.44.3 원칙)

## 결정 (2026-08-02) — 옵트인 유지, 대신 "켜는 순간 완성품"

유저 문답: "상태창에 날짜·시간 넣는 건 무조건 시간 탭으로 쓰게 해야 할 듯. 아예 시간
활성화를 기본으로 하는 게 더 나을려나?" → **기본 활성화는 안 한다.** 대신 셋을 건다.

1. **상태창의 날짜 자리는 시간 탭으로만 통하는 문.** 상태창 탭에서 `day` 같은 int 변수를
   손으로 만들어 행에 꽂는 길이 열려 있는 한, 사람도 AI도 계속 그리로 샌다 —
   §문제 진단 5건이 전부 그 길에서 났다. 상태창엔 자리만 두고 누르면 시간 탭으로 보낸다.
   켠 뒤에는 `{date}`·`{clock}` 노출 이름을 쓰게 한다. (이 항목이 옛 §열린 문제 "상태창 표시"의 답이다.)
   - 상태창을 AI에게 맡기는 슬라이스(→ design-기능프리셋.md)의 규격서에도 못박는다:
     **"날짜 행을 직접 만들지 말고 노출 이름을 참조하라."**
2. **켤 때 진행 입구를 같이 고르게 강제한다** — 액션(`[💤 하루를 마친다]`) / `skip_day` 보고 /
   `perTurn` 중 택1. 이유: `advance` 기본값이 `explicit`이라 **켜기만 하면 시계가 멈춘다.**
   상태창에 `2026-01-01 09:00`이 영원히 박히는 건 날짜가 없는 것보다 나쁘다 —
   유저 눈엔 버그고, AI는 그 고정 날짜에 맞춰 서술한다. `daily` 템플릿이 이미 정답 형태다
   (§문제 진단 1의 "정답이 한 템플릿에만 있고 전파되지 않았다"를 여기서 전파한다).
3. **새 봇 시작 때 1회 질문** ("이 봇은 날짜가 흐르나요?"). 기존 봇은 무변화.

왜 기본 활성화가 아닌가 — 13템플릿 중 9개가 의도적으로 `time` 없이 돈다(장면 단위 봇엔
날짜가 할 말이 없다). 그리고 기본 활성화는 결국 **안 물어보고 얹어주는 것**이라,
"고정 프리셋을 넣는 순간 제작자의 작업이 망가진다"(design-기능프리셋.md §범위 확정)와
같은 사고다. 원칙 5(옵트인)와 프로젝트의 **"없음 = 꺼짐"** 불변식(에셋 팩 0개면 `assets`
키 자체를 지운다)을 그대로 지킨다.

## 실측 사고 (2026-08-03) — 500분 폭주와 그 원인

> "버튼 누르면 하루가 끝나버리길래 '캐릭터는 밤까지 잤다' 했더니 그 다음 아웃풋부터
> 매 동작이 막 500분씩 흐름 ㅋㅋㅋ" (v0.52 유저)

**보조 프롬프트에 시계가 한 줄도 없었다.** 메인 모델은 상태 블록으로 `3월 2일 (월) 08:30`을
매 턴 보는데, 정작 시간을 굴리는 쪽은 `skip_min 현재 0`만 보고 "몇 분 흘렀냐"에 답하고 있었다.

감지되는 것과 안 되는 것이 여기서 갈린다:

| 표현 | 델타가 글에 있나 | 시계 필요? | 사고 전 |
|---|---|---|---|
| "3일 후", "한 시간 뒤", "다음날 아침" | ✅ 그대로 | ❌ | 잘 됨 |
| 대화 한 토막·식사 (암묵 진행) | ❌ 하지만 desc가 표를 줌 | ❌ | 잘 됨 |
| **"밤까지", "저녁이 되었다"** | ❌ **목표 시각만** | ✅ | **깨짐** |
| 자정 넘김 (skip_day/skip_min 분리) | — | ✅ | **깨짐** |

한국어 RP의 시간 표현은 대부분 **절대 시점**이다. 그걸 델타로 바꾸려면 빼기가 필요한데
피감수(지금 몇 시)를 안 주고 있었다. `skip_min`의 desc가 시키던 "날짜가 넘어가면 skip_day를
올려라"는 **애초에 수행 불가능한 지시**였다 — 자정을 넘는지 알려면 지금 시각을 알아야 한다.

그리고 폭주가 반복된 이유: **보조는 자기가 방금 민 시계를 확인할 방법이 없다.** 매 턴 처음처럼
서사에서 "저녁/밤"을 읽고 그 간격을 통째로 다시 넣는다. 계기판 없는 추측항법이다.
`maxGain: 720`은 한 번의 크기만 막지 이 반복을 못 막는다.

### 처방 (v0.65) — 세 줄

```
[지금] 3월 2일 (월) 16:50                      ← 어디 있나
[직전 보조 호출 이후 이미 반영된 변화]           ← 방금 뭘 했나
- 시각 3월 2일 08:30 → 3월 2일 16:50 (500분 진행)
- 호감도 10 → 15 (+5) — 도서관에서 웃어 줬다
[규칙]
- 위 "이미 반영된 변화"는 시스템이 이미 끝낸 일이다. 같은 것을 다시 세지 마라.
- 시간은 [지금] 시각 이후로 새로 흐른 만큼만 …
```

원장은 `state.meta.lastChanges`에 산다. **채팅 텍스트에 싣지 않는 것이 핵심이다** — 유저가
제안한 시뮬봇 시절 OOC 시스템 메시지 방식(로어북으로 메인 모델에게 "+15 EXP" 줄을 뽑게 하는 것)은
같은 정보를 주지만 네 가지가 따라온다:

1. **이중 계산** — 다음 턴 보조가 서사에서 "+5"를 읽고 또 +5를 보고한다. 지금 고치는 그 버그다
2. **메인 모델이 흉내 냄** — 히스토리의 형식을 보고 숫자를 지어낸다 (기본 지침이 존재하는 이유)
3. **리롤 불일치** — 스냅샷은 되감기는데 텍스트에 박힌 숫자는 안 따라온다
4. 매 턴 누적 토큰

SimCore는 보조 프롬프트를 자기가 조립하므로 그 우회로가 필요 없다. 모델을 한 번도 안 거친
원본 숫자를 "이미 끝난 일"이라는 못과 함께 꽂으면 된다. (화면에 배너로 띄우는 것 자체는
별개로 안전하다 — 상태창은 표시 시점 렌더라 저장 텍스트를 안 더럽힌다.)

규율: 전송 단계 몫(액션·시간 소비)은 이어 붙이고 응답 단계에서 교체 → 누적 없음.
정기 틱(onTurn) 제외(매 턴 같은 줄이라 정보량 0), 8줄 상한, 우편함(`skip_*`) 제외(시각 줄과 중복).
**루아 브리지는 둘 다 제외** — 설치 시점에 한 번 굽는 템플릿이라 그때 값이 영영 박히고,
`time_epoch`은 `⟦cur:⟧` 치환 목록에도 없다 (이미지가 없는 것과 같은 계열의 제약).

## 열린 문제

- **초(`ss`) 노출 여부.** RP에서 초는 대개 노이즈다. 포맷 옵션으로만 열고 기본은 분까지.
- **요일 로케일.** `weekdays` 배열로 열어 뒀지만 시작 요일(월/일) 기준을 정해야 한다.
- **가짜 달력을 원하는 봇.** 판타지 봇은 "한 달 30일 × 12달"이 오히려 편하다.
  `calendar: "gregorian" | "flat30"` 같은 선택지가 필요할 수 있다 (베리디아가 360일 체계다).
- ~~**목표 시각으로 받기 (v0.65 후속 후보).**~~ → **이행: v1.19.0 시각 보고** (아래 §후속 2026-10-17).
  `[지금]`을 줘도 빼기는 여전히 모델 몫이었다. "밤까지 = 22:00"만 답하게 하고 델타는 엔진이 계산한다 —
  목록 기한을 `@450`(절대일)로 받는 것과 같은 원리, "산술은 시스템 몫".
- **중간 도약 입구.** 🌙는 다음 08:00으로 가는 버튼뿐이라 "밤까지만"에 해당하는 입구가 없다
  (제보의 발단). daily 템플릿의 🕐(2시간)처럼 시간 단위 버튼을 표준형에 넣을지.
- **`elapsed`와 구 `day`의 이름 충돌.** 마이그레이션에서 `day`를 지우고 `elapsed`로 갈지,
  `expose`에 `day` 별칭을 허용할지. 별칭이 호환에는 편하지만 두 이름이 같은 값이 되는 건 혼란스럽다.

## 선행 작업 (이 설계와 겹치는 v0.49 항목)

1. **romance 템플릿의 `onTurn day+1` 제거** → daily 방식으로. 이 설계와 무관하게 지금 틀렸다.
2. **린트: 시각/시간대 변수가 있는데 `onTurn`이 `day`를 매 턴 올리면 경고.**
3. **린트: 지시문 text가 보조 담당 변수를 조작하라고 지시하면 경고** — "지시문은 메인 전용,
   보조에게 줄 규칙은 `desc`/보조 지시란". 실측 사고 재발 방지.
4. **규격서에 "시간 진행" 절 신설.** 지금은 `onTurn day+1` 말고 참고할 패턴이 없어서
   AI가 스키마를 만들 때 계속 그것을 복제한다.

1·2·3·4는 이 설계를 안 해도 값이 있고, 하면 이 설계의 준비가 된다.

`[시간 체계 켜기]` 마이그레이션(정리 마법사 재사용) + 진단 시간 진행 가정 + **전 템플릿 오탐 0** +
테스트(윤년·월말·자정·요일·포맷 자릿수·건너뛰기·세이브 왕복) + 템플릿 하나에 실물 + 가이드 원고.
`time`이 없는 봇은 **아무것도 바뀌지 않는다.**

## 후속 — 흐른 시간 노출 + 시간 고정표 (v1.9.11, 2026-09-11)

**제보(커뮤니티, 롤 프로게이머 시뮬 제작자)**: "매 턴 자동 처리가 10분이나 10년이나 한 턴으로 잡아 시간당 소모를 쓸 수
없다. 한 턴의 정의가 LLM 응답 한 번이라 시뮬 기준으론 뜻이 없다." 맞는 지적 — 달력(`time`)과 정산(`onTurn`)이 서로
몰랐다. 얼헌은 거울 변수(`day_prev`, `elapsed - day_prev`)로 우회했지만 경과일 단위라 시간당은 못 하고 바이브 코딩이
잘 못 짠다.

**유저 결정**: "AI가 시간을 조절하는 걸 기본으로 그대로 두고, 특정 행동이나 상황을 사람이 정하면 그것만 따로."
서사를 자연스럽게 따라가는 건 장면을 읽는 AI뿐이다 — 추정을 끄는 게 아니라 **오차가 새는 자리를 막는다**.
(검토했다 버린 것: `turn.basis: response|time|action` 스위치 — basis를 고르게 하는 대신 노출 이름 셋으로 같은 결과를 얻는다.
`time.estimate:false`(추정 끄기)도 보류 — 고정표가 그 자리를 더 부드럽게 채운다.)

1. **`turn_min`(예약 키)·`turn_hour`·`turn_day`(lookup 파생)** — 이번 정산에서 흐른 시간. 두 번의 시간 소비(전송 단계
   액션분 + 응답 단계 보조분)가 쌓이고 응답 단계 끝(이벤트 뒤, 턴 카운터 앞)에 0. onTurn이 `hunger - turn_hour * 5`로
   시간 비례 소모를 쓴다. 시간이 안 흐른 턴은 0 → 쿰질 대화는 안 깎인다. perTurn(1턴=1일)도 1440이 쌓인다.
2. **`time.pins` 시간 고정표** — `{ action | mentions, min, mode: set|add }`. 액션 항목은 전송 단계(효과 뒤, 소비 앞)에서,
   낱말 항목은 응답 단계(보조 델타 뒤, 소비 앞)에서. set은 그 턴의 보조 추정을 버리고(액션 set이면 깃발 `meta.timePin`으로
   응답 단계까지 이어져 보조 허용에서 skip_min이 빠지고 프롬프트에 "굳혔다" 한 줄), add는 위에 더한다.
   **skip_day는 안 건드린다** — 날짜 도약은 유저 선언이라 원칙("달력은 서사를 따라간다")대로 이긴다.
3. 편집기 [시간] 탭 "시간 고정표" 카드(행동·낱말·분·방식), 매 턴 규칙 카드 안내, 규격서 시간 탭·시간 규칙 묶음에
   "매 턴 소모를 응답 횟수에 걸지 마세요". 검증은 schema.md 참조. test-timepins.js.

**남은 생각**: 보조 추정을 분 자유 기입이 아니라 단계(0·15·60·360·1440)로만 받게 하면 편차가 더 준다 — skip_min의
`desc` 문구로 먼저 해 보고, 효과가 있으면 규격서 기본 문구로 올린다. (→ v1.19.0 시각 보고가 이 자리를 더 근본적으로 채웠다)

## 후속 — 시각 보고: 보조는 시각을 읽고, 빼기는 시스템이 (v1.19.0, 2026-10-17)

**제보(커뮤니티)**: "심코어 타임이랑 LLM이 인식하는 타임이 안 맞아서 이거 매칭시키는 걸 고민 중." 같은 글에 "LLM에게 매턴 시간을
표시하라고 하면 상태창과 이중 표시 + LLM의 엉성한 시간 관리가 겹쳐 미스매치가 난다"도 있었다 — 그쪽(요약용 시간 출력)은 v1.18.3
요약 도장으로 필요가 없어졌고, 남은 것이 시계 자체의 어긋남이다. 유저 결정: 진행.

**뿌리 셋** (§열린 문제 "목표 시각으로 받기"가 예고한 그대로):
1. 보조가 [지금]에서 직접 뺐다 — "저녁이 되었다"면 570, 자정을 넘기면 일·분 쪼개기. 한국어 RP의 시간 표현은 대부분 절대 시점이다(§실측 사고).
2. **skip_day는 시각을 보존한다** — 22:00에 자고 07:00에 깨는 것을 skip_day·skip_min 둘로는 적을 수조차 없다(skip_day 1 = 다음 날 22:00,
   skip_min은 음수 불가). 규칙 문구 "자정을 넘길 때만 skip_day, skip_min엔 그날 안의 분"은 그 경우 수행 불가능한 지시였다.
3. 분 델타는 두 번 세면 두 배라 상한(템플릿 240·720)을 걸었고, 그 상한이 정당한 도약("저녁까지 잤다")을 잘랐다 → 서사는 저녁, 시계는 오후
   → 다음 턴 메인은 상태 블록과 대화 기록 사이에서 헷갈린다. v1.18.3 요약 도장도 이 시계에서 나오니 같이 틀린다.

**처방**: 시계를 보이는 봇 + 보조에게 skip_min이 열린 턴이면, 보조는 최상위 `"clock": "HH:mm"`(이번 서사가 끝난 시각)과 — 날짜가
바뀌었으면 — skip_day만 적는다. 엔진(응답 단계 5.35)이 `목표 = 오늘 0시 + skip_day일 + clock`, `흐른 분 = 목표 − 지금`을 구해
skip_day/skip_min에 옮기고, 그 뒤는 종전 길(고정표 5.45 · 소비 5.5 · turn_min)을 탄다. 시각은 두 번 적어도 같은 시각이라
**이중 계산이 구조적으로 없다** — 같은 "18:00"이 다시 오면 0분. 이게 상한을 풀어도 되는 이유이지만, 봇이 건 maxGain은 그대로 둔다
(좀비의 4시간은 생존물 템포라는 의도다). 상한에 걸려도 다음 턴의 같은 시각이 나머지를 메운다 — 쌓이지 않고 수렴.

| 자리 | 규칙 | 이유 |
|---|---|---|
| 시각이 거꾸로(날짜 신고 없음) | 6시간 안이면 자정 넘김, 밖이면 버림 | 23:30 → 01:00은 넘김, 21:00 → "09:00"은 회상·약속 속 시각을 옮겨 온 것 |
| 날짜 창구 없음 + 하루 닫기 버튼 | 시각으로 자정을 안 넘긴다 | 날짜는 버튼·day_passed 정산의 몫 (일상·좀비) |
| day_passed 신고 | 시각을 버린다 | 하루 닫기 정산이 시간을 정한다 |
| 액션 timePin · 낱말 고정표 set | 고정표가 이긴다 | 사람이 정한 값 > AI 추정 (v1.9.11 원칙 그대로) |
| 시간을 정하는 이벤트가 걸린 턴 | 시각 보고가 비킨다 | day_break_sync의 "다음으로 돌아오는 그 시간대"가 옮겨진 시계에 또 더해 하루가 두 번 간다 |
| 시각 없이 분만 옴 | 분을 종전대로 | 예전 방식으로 답하는 보조도 받는다 |
| 루아 브리지 | 종전대로 분 | 굽는 템플릿엔 [지금]이 없다 |

시계를 안 보이는 봇(하루 단위 — 베리디아·얼헌)은 해당이 없다: 그 시계는 종일 시작 시각이라 시각을 받으면 그게 지어낸 시각이다
(v1.18.3 도장도 같은 판정 `time.clockExposed`로 날짜만 찍는다). 대상: 템플릿 일상·로맨스·좀비 + 조퇴악녀 + 아틀리에.

**알려진 남은 것** (→ v1.19.1에서 닫음, 아래): 로맨스식 하루 경계(🌙 + wake_at)에서 보조가 skip_day 1까지 적으면 하루가 두 번 간다 —
시각 보고 이전부터의 일(schema.md "하루 경계 넘김" 절). 테스트: `테스트/test-clockreport.js`.

## 후속 — 날짜가 하루 더 가는 두 자리 (v1.19.1, 2026-10-17)

v1.19.0을 유저에게 설명하다 찾았다. 둘 다 "하루가 더 간다" 쪽이고, 유저 결정: 고친다.

1. **새벽잠** — v1.19.0 시각 규칙의 날짜 예시 "(자정을 넘김·자고 일어남·며칠 뒤)"는 새벽 1시에 잠들어 같은 날 07:00에 깬 장면에도
   보조가 skip_day 1을 적게 했다(종전 분 규칙 "자정을 넘길 때만"보다 헐거웠다). 문구를 달력 기준으로 — "[지금]의 날짜에서 넘어간 날 수:
   밤에 자고 이튿날 깼으면 1, 자정 넘긴 새벽에 잠들어 같은 날 아침에 깼으면 0". 안전망은 엔진에: 자정~05:00에 skip_day 1인데 시각이
   지금보다 뒤면 같은 날로 받는다. 새벽의 "이튿날·내일"은 사람 말로 다가오는 아침이다(02:00의 "내일 아침" = 오늘 아침). 2 이상은 그대로.
2. **🌙 메아리** — 버튼이 넘긴 밤을 보조가 skip_day로 또 넘긴다. 로맨스 desc가 "자고 일어나 이튿날이면 1"이라 **시킨 대로 적으면** 이틀 뒤였다
   (깃발 꼴: 버튼은 day_break만, 동기화 이벤트가 "다음으로 돌아오는 아침"으로 — 그런데 소비 5.5가 이벤트 7보다 먼저라 skip_day가 먼저
   다음 날 같은 시각으로 옮긴다). 아틀리에 꼴(버튼이 시계를 바로 07:00으로)도 보조가 그 밤을 또 세면 같다. 템플릿 desc를 고쳐도 이미 만든
   봇은 옛 사본을 들고 있어서 **엔진에서** 막는다 — day_passed 유령 밤 빗장의 숫자판(5.33).

| 자리 | 규칙 | 이유 |
|---|---|---|
| 버튼이 이번 전송에 발동 / 버튼의 깃발이 서 있음 | 보조가 올린 skip_day에서 하루 | 그 밤은 버튼·동기화 몫. "사흘 뒤" 3 → 2 + 버튼의 하루 |
| 깃발 + 동기화가 도는 턴 | 보조가 적은 skip_min을 버린다 | 그 분은 "다음으로 돌아오는 그 시간대"를 넘겼을 때만 결과를 바꾼다 — 넘기면 동기화가 이튿날 그 시간대로 또 간다(같은 증상의 두 번째 길). 안 넘긴 분은 어차피 흡수 |
| 깃발 | 버튼이 세우고(bool) 시간 이벤트가 내리는 변수 | 버튼이 시계를 바로 옮기는 봇엔 없다 — 그쪽은 발동한 그 전송만 |
| 깃발이 서 있는 동안 | 시각 보고를 안 묻고(종전 분 규칙) 안 받는다 | 보조가 wake_at을 빠뜨린 턴에 받은 시각이 시계를 아침으로 옮기면 다음 턴 동기화가 또 더한다. 묻고 버리면 시계가 멈춘다 |
| 자정~05:00 + skip_day 1 + 시각이 지금보다 뒤 | 같은 날 | 새벽의 "이튿날" |

**대가**: 낮에 🌙을 누르고 "이튿날의 더 늦은 시간대"(10:00 → 이튿날 저녁)를 쓰면 하루가 당겨진다 — 다음으로 돌아오는 저녁이 그날 저녁이라.
v1.19.0까지는 보조의 skip_day 1이 겹쳐서 맞췄지만 이제 빠진다. 흔한 쪽(밤 🌙 → 다음 날 아침)과 바꾼 드문 쪽이다.
같은 결로 아틀리에 꼴에서 🌙과 "며칠 뒤"를 한 턴에 쓰면, [지금](이미 아침) 기준으로 센 보조의 일수가 하루 모자랄 수 있다 — 드물다.
