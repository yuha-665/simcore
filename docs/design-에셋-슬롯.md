# 설계 초안 — 에셋 슬롯 (이미지 태그 자동화)

> 2026-07-30, 맨션봇 개조 세션에서 이어진 설계 논의 정리. **미구현.**
> 배경 제보: "에셋 출력식도 매번 보내서 토큰 낭비 심한데 이것도 심코어에서 제어 가능하려나" +
> "캐릭터.감정 / 캐릭터.감정.의상 이렇게 조합하게 하거나, 아무튼 키워드별로 나눠서 담을 수 있게" +
> "몇 칸으로 쪼갤지는 자유롭게, 각 칸에 어느 키워드 관리할지 하게 하면 감정이랑 성인 키워드는
> 공용으로 돌려쓰고 캐릭터명만 앞에서 변하니 비용 좀 싸지지 않나".

## 문제 진단

감정 이미지를 쓰는 봇은 매 턴 프롬프트에 이런 걸 싣는다 (실측: 맨션봇 8인 봇):

1. **`{{assetlist}}` 통짜 덤프** — `{{join::{{filter::{{assetlist}}::unique}}::{{br}}}}`.
   에셋이 인물 8 × 표정 70이면 **560줄**. 아래 키워드 목록 전체보다 무겁다. 매 턴.
2. **수동 키워드 목록** — 인물 8 + 표정 70 + 성적 45 + 지침 문단. 700~900토큰 추정. 매 턴.
3. 성적 키워드는 대부분의 턴에서 완전한 낭비인데도 상시 실린다.

**핵심 통찰(유저): 조합(C×E)을 슬롯(C+E)으로 바꾸면 목록이 곱셈에서 덧셈이 된다.**
8×70 = 560 → 8+70 = 78. 감정·성인 키워드는 인물과 무관한 **공용 축**이라 한 번만 적으면 된다.

## 확정 사실 (구현 전 조사 완료)

- **output 핸들러가 저장 본문을 반환한다.** `addRisuScriptHandler('output', ...)`가 `content`를
  돌려주는 구조이고, 지금도 여기서 `⟦simcore:N⟧` 마커를 붙인다 (risu-plugin.js ②③ 구간).
  → **본문 앞/사이에 `<img="...">`를 심는 건 이미 가능한 일.** 유저가 걱정한 "아웃풋 수정" 능력이 이미 있다.
- **보조 호출이 그 핸들러 안에서 await로 끝난 뒤 content가 반환된다.** 즉 보조가 고른 값을
  **그 턴 본문에** 넣을 타이밍이 확보돼 있다. suggest(v0.43)가 정확히 이 경로.
  → 상태 갱신 호출에 피기백하면 **추가 LLM 호출 0**.
- **플러그인이 에셋 목록을 읽을 수 있다.** `Risuai.getCharacter()` → `additionalAssets:
  [이름, assetId, 확장자][]` (schemas.md). [live-test] 권한·실제 접근 확인 필요.
- **CBS로는 assetlist를 인물별로 못 거른다.** `{{filter::배열::all|nonempty|unique}}` 뿐 —
  "이름에 X가 든 것만" 필터가 없다. 즉 이 문제는 **CBS로 못 풀고 플러그인으로만 풀린다.**
- 표시 정규식(`<img="(.*?)">` → div)은 display 단계라 토큰과 무관. 그대로 둔다.

## 스키마 (초안)

```json
"assets": {
  "sep": "_",
  "slots": [
    { "id": "who",  "label": "인물", "values": ["Hiromi", "Seiko", "…"] },
    { "id": "emo",  "label": "감정", "values": ["angry", "happy smile", "…"] },
    { "id": "wear", "label": "의상", "optional": true, "values": ["…"] }
  ],
  "by": "main",
  "format": "<img=\"{name}\">",
  "gate": [{ "slot": "emo", "values": ["…성인 키워드…"], "when": "nsfw_on" }]
}
```

- **칸 수 자유** — `slots` 배열 길이가 곧 칸 수. 각 칸이 무엇을 관리하는지는 `label`이 정한다.
- `optional: true`인 칸은 빼고 조합해도 된다 (`인물_감정` / `인물_감정_의상` 둘 다 유효).
- `format`의 `{name}`에 조합 결과가 들어간다. 봇마다 표시 규약이 달라도 여기서 흡수.
- `gate` — 특정 칸의 **일부 값 묶음**을 조건부로만 노출 (성인 키워드가 1순위 용도).
  조건은 기존 수식 문법 그대로. 액션 무장(`hold`) 기반이 가장 확실하다.

## 두 가지 모드 — `by`

| | `by: "aux"` | `by: "main"` |
|---|---|---|
| 메인 프롬프트 비용 | **0** (목록을 아예 안 실음) | 슬롯 목록 C+E (560→78) |
| 배치 | 메시지당 1개(맨 앞)가 안정적 | 문단 사이 자유롭게 여러 개 |
| 정확도 | 실존 대조 가능 → 깨진 이미지 0 | 모델이 조합 (대조 불가) |
| 추가 호출 | 0 (상태 갱신에 피기백) | 0 |

- **aux**: 보조 응답 JSON에 `"image": { "who": "Hiromi", "emo": "angry" }` 를 얹어 받고,
  SimCore가 조합·대조해서 output 핸들러에서 본문 맨 앞에 삽입.
- **main**: 슬롯 목록 + 조합 규칙을 **지시문 형태로** 메인 프롬프트에 주입. 지금 손으로 쓰던
  블록을 SimCore가 대신 쓰되, 곱셈이 덧셈이 되고 `gate`로 안 쓰는 묶음이 빠진다.

**둘 다 지원한다.** 연출 밀도(문단마다 표정이 바뀌는 봇)와 비용 중 무엇을 살릴지는 봇마다 다르다.

## 슬롯 자동 감지 (편집기)

`[에셋에서 슬롯 자동 감지]` 버튼:
1. `getCharacter().additionalAssets`에서 이름만 뽑는다
2. `sep`으로 쪼개 **칸 수의 최빈값**을 잡고, 칸별 고유값 집합을 만든다
3. "1칸 8종 / 2칸 70종 / 3칸 4종" 으로 제시 → 유저는 **칸마다 이름표만** 단다
4. 칸 수가 들쭉날쭉하면(2칸·3칸 혼재) 짧은 쪽을 기준으로 잡고 나머지를 `optional` 칸으로

에셋을 못 읽는 환경이면 이 버튼만 비활성, 손으로 채우는 경로는 그대로 둔다.

## 실존 대조 (깨진 이미지 0)

슬롯 방식의 유일한 약점은 **비어 있는 칸 조합**이다 (Hiromi엔 있는 표정이 Seiko엔 없음).
에셋 이름 집합을 Set으로 들고 있다가:
- `aux` 모드: 조합 결과가 집합에 없으면 **삽입 생략** (또는 같은 인물의 지정 폴백 감정으로 강등)
- `main` 모드: 대조가 불가능하므로 주입문에 "확신이 없으면 태그를 생략하라"를 항상 깐다

## 열린 문제 / 범위 결정

- **다중 삽입 위치.** `aux`에서 문단 사이사이 여러 장을 넣으려면 보조가 위치까지 정해야 하는데
  ("N번째 문단 뒤") 어긋나기 쉽다. v1은 **메시지당 1장(맨 앞)** 으로 시작하고, 다중은 `main` 몫.
- **루아 브리지 경로.** 보조 결과가 지연 적용(retro)이라 이미지도 한 턴 늦게 붙는다 —
  suggest와 같은 제약. 문서에 명시하고, 브리지 모드에서는 `main`을 권장.
- **화자 판별.** `aux` 모드에서 "이번 장면의 주인공이 누구인가"를 보조가 골라야 한다.
  SimCore가 이미 아는 것(`*_spot` 같은 위치 변수)을 후보 좁히기에 쓸 수 있는지 검토.
  다만 슬롯 값과 변수를 잇는 배선(`from: "var:noz_spot"`)은 v1 범위 밖으로 둔다.
- **기존 봇과의 공존.** 손으로 쓴 블록을 그대로 둔 채 이 기능을 켜면 중복 주입이 된다.
  켤 때 "기존 이미지 지시 블록을 로어북에서 빼세요" 안내가 필요하다.
- **표정 목록은 안 줄어든다.** 인물과 무관한 공통 축이라 쪼갤 축이 없다. 절감의 대부분은
  ① assetlist 덤프 제거 ② 성인 묶음 gate ③ 곱셈→덧셈 에서 나온다.

## 완료 정의

스키마 `assets` 섹션 + 검증 + 편집기 탭(슬롯 행·자동 감지·모드·gate) + `main` 주입문 생성 +
`aux` 피기백/조합/대조/본문 삽입 + 실존 대조 폴백 + 테스트(슬롯 파싱·조합·대조·두 모드 배선) +
템플릿 하나에 실물 예시 + 가이드 원고. 기존 봇은 `assets`가 없으면 **아무것도 안 바뀐다.**
